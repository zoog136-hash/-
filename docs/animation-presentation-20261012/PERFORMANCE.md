# 전투 성능 비교

**전체 프레임 성능이 개선되었다고 판정하지 않는다.** 추가 모션의 CPU 비용을 줄였지만 최종 일반 사냥/보스 결과에는 증가한 값과 감소한 값이 함께 있다. 192마리 밀집 전투는 이 소프트웨어 렌더 환경에서 여전히 무겁다. Android 실기기 FPS나 프레임 유지 보장 수치가 아니다.

## 환경과 방법

- Godot 4.7.2 / Linux x86_64 / AMD EPYC 9V74, 표시 CPU 5개·cgroup CPU 할당 4개. OpenGL 4.5, Mesa 25.0.7, llvmpipe(LLVM 19.1.7), Xvfb 1280×720. VSync 변경은 드라이버에서 지원되지 않았다.
- 시작 main 별도 worktree와 최종 feature에서 **동일한** `benchmark_presentation_battles.gd`를 순차 실행했다. 다른 Godot 작업과 겹치지 않았다. 첫 결과의 증가를 확인한 뒤 CPU 비용을 분리 측정하고 최적화, 시작 main 재측정, 최종 재측정을 수행했다. 중간 측정도 삭제하지 않았다.
- 일반 사냥 32/96/192마리, 기존 드레이크 1마리+나머지 일반 몬스터를 합쳐 32/96/192마리인 보스 전투를 구분했다.
- 실제 Main.tscn, AI, AUTO, 피해 신호, 투사체, 기존 아트를 사용한다. 개체 수 유지를 위해 **진단 스크립트 내부에서만** HP/공격력/레벨/AC와 일반 몬스터 공격 방식을 통제했다. 보스의 기존 기본 방식·특수기는 보존했다. 게임 데이터는 바꾸지 않았다.
- 시나리오마다 60프레임 준비 후 180프레임의 `process_frame` 간격과 Godot process/physics monitor를 수집했다. 짧은 단일 시나리오 샘플이고 동작/접촉/타깃 경로와 서버 변동이 있으므로 정밀한 인과 추정이나 기기 보장으로 쓰지 않는다.
- 렌더 프레임 수가 고정되어도 실제 경과 시간이 다르므로 두 실행의 누적 타격 수를 공격속도 변화의 증거로 비교하지 않는다. 공격당 1회/마커 시계/변신 중 연속성은 별도 결정적 회귀 검사로 검증했다.

## 실제 프레임 간격(ms, 낮을수록 좋음)

| 시나리오 | 수 | main 1 중앙 / p95 | main 재측정 중앙 / p95 | 최종 중앙 / p95 | 최종 중앙 vs main 1 |
|---|---:|---:|---:|---:|---:|
| 일반 사냥 | 32 | 34.96 / 48.73 | 34.52 / 47.84 | 34.03 / 46.52 | -2.6% |
| 일반 사냥 | 96 | 67.16 / 86.39 | 68.44 / 93.43 | 69.10 / 87.24 | +2.9% |
| 일반 사냥 | 192 | 140.16 / 191.52 | 141.02 / 174.79 | 146.03 / 167.33 | +4.2% |
| 보스+일반 | 32 | 36.79 / 48.56 | 36.17 / 47.61 | 39.86 / 61.88 | +8.3% |
| 보스+일반 | 96 | 69.90 / 82.43 | 70.10 / 102.62 | 69.43 / 86.81 | -0.7% |
| 보스+일반 | 192 | 143.01 / 159.78 | 150.33 / 183.01 | 149.43 / 175.68 | +4.5% |

위 값은 FPS로 환산하거나 Android 성능으로 표시하지 않는다. 예를 들어 보스 192마리의 시작 main 자체도 중앙 143.01→150.33ms, p95 159.78→183.01ms로 달라졌다. 단일 관측의 증감을 모두 코드 효과로 단정할 수 없다. 최종에서도 일부 회귀 가능성이 남아 있어 모바일 성능 승인 상태로 표시하지 않는다.

## 모션 자체 CPU 비용

기존 `benchmark_actor_motion.gd`: GPU 제외, 256개 `advance/apply`, 준비 1회 후 360 tick×5회 중앙값. 전투 전체 수치와 혼합하지 않는다.

| 대상 | main (ms/256개 tick) | 중간 구현 | 최종 모션 코드 |
|---|---:|---:|---:|
| 기본 캐릭터 시트 | 1.166 | 1.638 | 1.362 |
| 일반 몸체 | 0.696 | 0.937 | 0.772 |

중간 구현 대비 중복 삼각함수/구간 보간, 기본 시트 트랙 검색, 체형 uniform 갱신을 줄였다. 일반 원화 개체의 빈 드로잉과 보스 전용 시계 호출도 생략했다. 최종 모션은 시작 main보다 기능과 CPU 비용이 모두 추가되어 있으며, 이 작은 비용을 0이라고 보고하지 않는다.

## 풀·노드·가독성

| 수 | 최종 peak nodes(두 시나리오 동일) | VFX/투사체 반환 | 고아 노드 |
|---|---:|---|---:|
| 32 | 6795 | 모두 반환 | 0 |
| 96 | 7307 | 모두 반환 | 0 |
| 192 | 8075 | 모두 반환 | 0 |

최종 전체 실행의 VFX high-water는 62개로 기존 160개 풀 이내다. 이 값은 시나리오 사이에 초기화하지 않은 **누적 최대값**이다. 각 시나리오 종료 시 VFX/투사체가 반환되며 공격 중 실제 피격 콜백이 발생했다.

192마리를 좁은 공간에 배치한 화면에서는 기존 이름표·HP 바가 심하게 겹쳐 몸체를 가린다. 추가 보스 효과의 노드/수명 제한은 작동하지만 이 밀집 화면 전체의 가독성이 해결된 것은 아니다. 이름표 LOD와 Android GPU/발열/배터리 측정은 남은 과제다.
