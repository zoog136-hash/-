# Android 523.843: distinguish script time from elapsed frame gaps

Same phone report, not a controlled comparison to older builds. 10,700
frames: 6,738 over 16 ms, 5,647 over 16.667 ms, 1,261 over 33 ms, 298 over
or equal to 100 ms, three at least 4 seconds. Of the nine worst retained
intervals below 4 seconds, the largest measured phase in seven is
post-draw callback to next SceneTree signal. One is predominantly before
pre-draw and one is after next signal but before the frame probe. Do not
combine those paths or blame GPU, sleep, saves, or A* from elapsed time alone.

The native bag outlier is 1,126 ms inclusive; 1,028 ms is the native stage,
including 359 ms model and 409 ms visible lines. The 302 ms across 20 icon
owner calls overlaps visible lines. This patch stops the recognized native
icon route from running alternate supplier predicates whose results it was
already ignoring, including a lazy template expansion. Canonical item,
wrong row, original texture SHA, missing assets and test-item behavior
remain unchanged. The image pack reader and its storage-bake key are
unchanged: no expensive image catalog rebuild at the next update. No
claim that this eliminates the 302 ms icon interval.

## Pair the next slow frame with an optional Android trace

The report snapshots now carry two bracketing samples of realtime and the
same monotonic clock used by the existing Godot frame markers. Sampling is
done at report creation (approximately every 15 seconds, and on exit), not
in the frame loop. The recovery writer keeps only six numeric clock fields.
The Python tool keeps old reports useful as relative phase evidence. On
new reports it provides estimated realtime *ranges* from agreeing samples
and refuses to match wide brackets, timestamps outside the samples, and
offset changes over 20 ms. These endpoints cannot detect a clock step that
was later undone; compare only the bounded onscreen session. A platform
suspend, missing clock snapshot or insufficient trace overlap makes
absolute correlation unproven.

With an already authorized ADB connection, from the repo root:

```sh
adb shell perfetto -c - --txt -o /data/misc/perfetto-traces/twilight-play.pftrace \
  < tools/android/twilight_playback_trace.pbtxt
adb pull /data/misc/perfetto-traces/twilight-play.pftrace .
python3 tools/android/analyze_hitch_alignment.py /path/to/TWILIGHT-performance.json
```

Start the capture in the already loaded gameplay screen, then reproduce
movement, automatic hunting, native bag opening and draw. End the game
normally afterward for the JSON. Compare the exact same interval in Perfetto
using clock snapshots and app thread scheduling/presentation, not by
matching two unrelated pauses of similar duration. Android 12+ FrameTimeline
availability on a particular surface is conditional; if it gives no
usable surface, use scheduler thread evidence and explicitly report the
missing presentation observation. The trace is opt-in, not run by the
game; it may include system process names. Keep it local unless choosing
to share it for diagnosis. This adds no logcat or input event content.

References: [Perfetto clocks](https://perfetto.dev/docs/concepts/clock-sync),
[Android recording](https://perfetto.dev/docs/learning-more/android), and
[FrameTimeline limitations](https://perfetto.dev/docs/data-sources/frametimeline).

The 523.843 file predates the new anchors and cannot be aligned
retrospectively. This work is diagnostic for unmeasured gaps, not a
performance claim or Android verification.
