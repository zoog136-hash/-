# 작은 조회 비용과 레거시 저장 가드 (2026-11-24)

이 후속이 최종 상태다. [직전 원본·퀘스트·저장 보고서](original523-cross-domain-save-20261124.md)의 16종 시간은 중간 커밋의 수치이고, 아래는 안전 가드를 포함한 최종 재실행이다.

## 가방의 보통 이름 조회에 퀘스트 전용 색인을 만들지 않는다

World의 `_find_catalog_item_record_cash_install`은 아이템 이름만 가지고 조회하면 **모든 이름**을 먼저 퀘스트 보상 소유자에게 물었다. 소유자는 보상 접두사 검사 *전에* 가방 사본/슬롯 수가 바뀌었는지 확인하고 실물 전부를 순회했다. 따라서 보상과 무관한 일반 화살 한 개를 조회해도 새 가방 전체를 읽었다. 없는 보상 이름은 첫 호출이 색인을 무효화한 뒤 World가 두 번째로 즉시 전체 가방을 훑었다.

이제 원본 소유자는 `[원본 보상] ` 이름만 받는다. 새 가방을 방금 확인한 뒤의 동일 이름 실패는 다시 훑지 않는다. 이미 만들어 둔 색인이 같은 크기의 실물 교체로 오래됐을 수 있으면 처음 요청에서도 새 항목을 찾도록 재확인한다. 명시적 원본 ID, 일반 카탈로그/동명이인 순서, 사용자 지정 소유자의 선점, 보상 레코드 사본의 독립성은 유지된다. 아이템 수량이나 사용 규칙, 이미지에는 손대지 않았다.

Headless Godot, 3,001개 합성 실물 가방으로 매번 같은 이전 동작과 실제 수정 World 조회를 12쌍 교차. 아래 첫 조회는 가방의 Dictionary가 바뀐 직후 한 번, warm 200은 같은 가방의 일반 조회 200회 합계다. 실제 폰에서 가방이 몇 번 바뀌었는지는 이전 JSON에서 알 수 없다.

| 경로 (ms) | 기존 중앙 / 최대 | 수정 중앙 / 최대 |
|---|---:|---:|
| missing_held | 3.677 / 4.806 | 2.103 / 3.240 |
| ordinary_after_bag_change | 1.846 / 2.392 | 0.040 / 0.328 |
| ordinary_warm_200 | 3.094 / 4.078 | 3.014 / 3.255 |

신규 검사 85/85. 현금상품 설치의 사용자 지정 소유자/호출 범위 37/37, 기존 프레임 경로 62/62. 전체 가방 열기·휴대폰 FPS가 이만큼 빨라졌다는 뜻은 아니다.

## 953KB 레거시와 v2 분리

중간 코드에서 계정 봉투 없는 레거시 저장도 완료 시 큰 데이터의 해제 위치가 바뀌었다. 과거/중간의 동일 레거시 파일을 한 프로세스에서 8쌍 교차하니 메인 완료 중앙이 **10.666→22.195ms**로 악화했다. 그래서 **레거시는 기존 worker의 payload와 동결 입력을 그대로 유지**하고 다시 측정했다. v2에서만 봉인된 개인 스냅숏과 검증된 SHA 소유권을 넘긴다. 두 경로 모두 전체 파일 SHA, 두 캐릭터 또는 레거시 봉투 없음, 작업마다 실제 채택 분기를 검사한다(각 74/74).

| 경로 (ms) | 기존 중앙 / 최대 | 수정 중앙 / 최대 |
|---|---:|---:|
| 레거시 worker_us | 207.542 / 296.983 | 153.491 / 293.743 |
| 레거시 main_publish_us | 14.316 / 25.646 | 15.011 / 17.442 |
| 레거시 total_us | 221.679 / 311.432 | 167.755 / 307.065 |
| v2 worker_us | 107.272 / 138.216 | 85.582 / 127.894 |
| v2 main_publish_us | 22.383 / 26.622 | 20.751 / 27.579 |
| v2 total_us | 125.555 / 162.160 | 108.682 / 153.665 |

레거시 중앙에는 변동이 남았다. 가드를 넣은 후 레거시 완료가 빨라졌다고 주장하지 않는다. v2의 최종 바이트와 필드 소유권은 동등하며, v2 전체 워커+완료 중앙은 줄었지만 메인 완료 최대는 더 나빠졌다. 모두 PC 측정이다.
