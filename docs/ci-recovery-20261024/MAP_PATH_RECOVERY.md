# main 통합 CI: 실제 문 표시 및 PNG 이동 경로 수정

기준 main은 `e0a14f07da7764598822be669d05b3c2985d13eb`이다. [통합 CI 39957518319](https://github.com/zoog136-hash/-/actions/runs/39957518319)에서 경로 검사 92개와 문 표시 검사 2개가 실패했다. 이 문서는 해당 원인과 실제 수정 범위를 기록한다. 전체 원본 지형 복원이나 Android 성능 검증을 뜻하지 않는다.

## 원인과 수정

### PNG 위에 사라진 실제 문 경계

PNG 청크는 기존 `RemakeChunk`의 source-edge 그리기 과정을 거치지 않았다. 실제 닫힌 문은 내비게이션과 물리에 남았지만 PNG 위에는 보이지 않았다. `remake_renderer.gd`에서 같은 `source_doors.flags`의 닫힌 경계만 PNG 위에 그린다. 문이 열리면 기존 상태 변경 감지가 청크를 다시 구성하면서 그 경계를 제거한다. PR #152의 `7d62e8f58` 및 #153의 `0fec87908`과 같은 수정이다.

### 중심점만 연결하던 길찾기

기존 `AStarGrid2D`의 두 셀 중심이 각각 비어 있어도 그 사이 선분은 실제 바위의 모서리나 검수 바닥 밖을 지날 수 있었다. 예를 들어 에스카로스 `(7001,2968) → (6761,2968)`은 `(6823,2968)`에서 기존 장애물에 걸린다. 대각선을 금지하는 것만으로는 해결되지 않았다.

기존의 안전한 경로는 유지한다. 경로가 실제 `line_clear` 검사를 통과하지 못할 때만, 기존 도달 가능 셀을 그대로 쓰는 별도 `AStar2D`가 통과 가능한 연결선을 찾는다. 연결선은 기존 4px 발 반경, 실제 장애물, PNG alpha 격자 및 검수 바닥 검사로 양방향 확인한다. 기존 `line_clear`, 물리 충돌, solid 셀, 스폰 후보는 완화하거나 제거하지 않는다.

직선으로 갈 수 있으면 즉시 반환한다. 검증된 내부 경로는 셀 쌍별 최대 128개까지 재사용하지만 이동한 시작점·목적지와의 연결선은 매번 다시 검사한다. 필드를 다시 구성하면 그래프와 캐시는 폐기된다. 셀 안에 많은 보조점을 추가하던 조사용 후보는 최종 구현에서 제거했다.

PR #152의 `4fa0354d9`는 셀 전체에 더 강한 polygon 발 검사를 적용하여 에스카로스의 기존 연결과 몬스터 배치를 끊었다. 그 커밋의 `configure_png` 안 전역 body-clear 셀 제거 및 `DIAGONAL_MODE_NEVER` 블록은 이번 수정에 포함하지 않는다. 기존 PR과 통합할 때도 그 블록을 다시 남기면 안 된다.

### 서로 맞지 않던 검수 데이터 세 곳

`native_png_navigation_corrections.json`은 두 기준 plan SHA와 원본 PNG SHA를 확인한 뒤 코드 측 계획에만 적용한다. 기존 PNG·manifest·pack index·plan SHA·일반 review SHA·저장 layout revision을 변경하지 않는다. 기존 세이브의 좌표계를 이전할 필요가 없다.

| 위치 | 원인 | 제한된 수정 |
|---|---|---|
| 에스카로스 `(8297,2168)`과 `(8297,2184)` 사이 | 기존 큰 바닥 polygon #3과 경로 끝 polygon #29 사이에 약 8px의 연속 polygon 공백이 있었다. 두 셀은 이미 물리적으로 열려 있었다. | `(8293,2167)`–`(8301,2185)`의 **8×18px** 연결 조각 한 개. 기존 open 셀 안에만 놓이며 solid/물리 격자를 바꾸지 않는다. |
| 에스카로스 검수 목적지 `(8260,2270)` | 중심 셀은 열려 있지만 4px 발이 옆 solid 셀에 걸렸다. | 같은 셀의 안전한 중심 `(8265,2264)`로 **7.81px** 교정. |
| 지배 정상 검수 목적지 `(8270,3660)` | alpha-solid 셀 `(392,172)` 안에 지정되어 있었다. | 같은 중앙 구역의 가장 가까운 안전한 셀 중심 `(8275,3669)`로 **10.30px** 교정. |

에스카로스 연결의 `(8297,2168)`–`(8297,2184)`를 2px 간격으로 검사한 중심·상하좌우 4px 발 표본 45개는 실제 PNG alpha가 모두 255였다. alpha가 곧 지형 종류라는 추론으로 다른 영역을 열지 않았다. 수정은 기존 두 검수 바닥 및 이미 열려 있던 물리 셀 사이의 작은 내부 불일치에 한정된다. 검수 목적지는 5+27개를 그대로 유지하고, 모든 목적지의 정확한 발 위치와 최종 도달점도 검사한다. NPC·포탈·스폰·몬스터는 이동하지 않는다.

## 검증

`tests/native_png_route_recovery_test.gd`: **1,554개 검사, 실패 0**. 두 맵의 전체 solid 셀·물리 직사각형·도달 가능 배열·모든 스폰 후보·몬스터 정체성과 수량·포탈·NPC·입장점·layout revision의 전후 일치를 확인했다. 32개 목적지 모두 정확히 도달하며 반환한 모든 구간이 기존 발 검사를 통과한다. 이동한 끝점의 캐시 재사용과 구성 변경 시 캐시 폐기도 검사한다. 전체 결과와 파일 SHA는 `map-path-recovery.json`에 있다.

| 변경하지 않은 기존 runtime 검사 | 최종 결과 | 시간 |
|---|---|---:|
| `hunting_paths_test` | **25맵, 10,666개 검사, 실패 0, 엔진 오류 0** | 123.904초 |
| `remake_door_runtime_test` | **14개 검사, 실패 0, 엔진 오류 0** | 9.490초 |

경로의 실제 반환 구간마다 수행하는 기존 assertion 때문에 경로 검사 집계는 이전 7,115개에서 10,666개가 됐다. 기존 25맵·목적지·직접 보행·우회·장애물·스폰 검사를 삭제하거나 조건을 완화하지 않았다. 최종 실행 시작/종료에 모든 관련 소스 SHA가 같았다. 테스트가 덮어쓰는 과거 검증 문서는 원래대로 복구하고 현재 증거만 이 디렉터리에 보존했다.

환경 준비 중 새 PNG를 가져오기 전에 실행한 시도와 가져온 PNG의 Godot import가 끝나기 전 시도에는 `warrior.png` 로더 오류가 있었다. 이 시도들은 최종 통과로 집계하지 않았다. 위 결과는 최종 import 후 격리된 사용자 저장 경로에서 다시 실행한 결과다.

| 측정 | 결과 |
|---|---:|
| 첫 에스카로스 보완 경로: 그래프 생성 포함 | 313.172ms |
| 같은 대표 장거리 경로 100회 평균 | 1.490ms |
| 짧은 직선 경로 100회 평균 | 0.023ms |
| 에스카로스 보완 그래프 | 기존 셀 21,811개 |
| 27목적지 조회 후 엔진 static memory 증가 | 21,870,224바이트, 약 20.86MiB |

관측된 edge 캐시는 58,322개, 내부 경로 캐시는 24개였다. 128개 상한은 코드로 강제하지만 129번째 키의 FIFO 퇴출을 별도로 측정한 결과는 아니다. 필드 참조를 해제한 뒤 그래프의 `WeakRef`가 실제로 해제되는 것을 확인했다.

Linux headless 단일 실행 수치이며 Android FPS나 기기 최대 메모리 측정이 아니다. 첫 보완 경로에는 약 0.31초와 위 그래프 메모리 비용이 남는다. 아덴/신념 배율이나 PR #155의 raster 생성·진입 최적화·청크·미니맵 코드는 변경하지 않는다.
