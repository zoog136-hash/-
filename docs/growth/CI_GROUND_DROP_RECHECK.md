# cae446ce item-options / ground_drop_smoke_test 귀속 조사

## 결론

성장 UI나 growth 저장 키 수정이 만든 줍기/저장 기능 회귀는 아니다. main의 원래 검사는 통과하며, CI 복구가 편입된 현재 코드에서는 오래된 **테스트 좌표 선택 조건** 때문에 7건이 연쇄 실패한다. 따라서 이 실패를 main의 기존 실패로 분류하지 않는다. 편입된 경로 복구의 정상적인 한 도착점 경로와 테스트의 두 경유점 가정이 충돌한 것이다.

`163319a1`과 `cae446ce`의 줍기 관리자/제어기/인벤토리 전달기/World/NativePngField/검사/좌표 helper는 바이트 단위로 같다. 마지막 성장 저장 키 수정이 원인은 아니다. 별도 `163319a1` 전체 실행은 반복하지 않았으며 파일 동일성만 확인했다.

## 실제 재현

- 현재 HEAD의 원본 검사: CI와 같은 7개 실패를 독립된 새 저장 디렉터리에서 재현했다.
- 같은 기반 main의 원본 검사: PASS.
- 현재 HEAD의 좌표 진단: 검수된 200px 직선 목표 `(66410, 19998)`로 가는 경로는 `[(66410, 19998)]` 한 점이며 `line_clear=true`다. 현재 `NativePngField.path()`가 이 정상적인 직선 경로를 도착점 한 개로 반환한다. 플레이어/줍기 제어기는 원래부터 비어 있지 않은 경로를 지원한다.
- 기존 테스트는 `path.size() < 2` 조건으로 이 정상 목표를 건너뛰고 다른 목표 `(66100.4, 20107.6)`를 택했다. 해당 위치는 중심만 `walkable=true`이고 실제 4px 발판 `point_clear=false`, 자기 위치까지의 `line_clear=false`다. 테스트가 플레이어를 그 좌표로 직접 옮겨 줍기가 거절된 것이다.
- 실패한 수동 아이템이 남아 AUTO와 이후 바닥 스냅샷의 개수도 연쇄 어긋난다. 스냅샷/복원 실패가 별도의 growth 저장 직렬화 손상을 뜻하지 않는다. 이 스모크 검사는 전체 캐릭터 저장 대신 바닥 아이템 스냅샷을 검사한다.

## 제한된 수정

`tests/ground_drop_smoke_test.gd`의 좌표 선택만 수정했다. 정상 경로의 경유점 수가 아니라 비어 있지 않은 경로와 실제 줍기 반경 내 도착점을 요구한다. 플레이어를 옮길 위치와 13px 옆 AUTO 드랍 위치 사이도 실제 시야/발판 검사를 통과해야 한다. 줍기 반경은 런타임의 기존 상수를 읽는다.

기존 단언 25개를 **모두 그대로 보존**했다. 새 단언 3개로 (1) 시작점이 실제 줍기 반경 밖인지, (2) 계획 경로가 실제 줍기 범위까지 도달하는지, (3) 플레이어 발판과 인접 AUTO 드랍의 시야가 유효한지를 확인한다. 실패를 무시하거나 건너뛰지 않는다. 빈 좌표를 찾지 못하면 기존 setup 단언이 그대로 실패한다. 생산 코드의 벽·시야·줍기 반경·수명·최소 노출 시간은 바꾸지 않았다.
