## Results, failure and idempotence

- Pre-save or definite unchanged-file failure: existing guarded population/boss/catalog/field/options/time/RNG restoration remains. A prepared action token is never used as permission to run cancellation on an unsaved route.
- Save uncertain or committed-file proof rejected: hold saving/travel/exit, preserve both owner/resource sets and evidence, keep auto off and actors disabled. No cleanup, catalog rollback, refund or automatic retry.
- Catalog finish conflict: same post-save hold; no false restore or activation.
- Cleanup rejection (`transient_mutation:false`) becomes CLEANUP_CONFLICT. Partial/context-changing/unknown cleanup (`transient_mutation:true`) becomes CLEANUP_UNCERTAIN. Both retain actual receipts, keep actors disabled and do not refund/rollback/retry after authoritative save.
- Reentrant completion sees CLEANUP_RUNNING and stays held. A completed repeated callback must match the original payment, accepted context, epoch and NPC model, and returns the cached result with already_finished:true without running cancellation, saving, retirement or actor activation again.
- Success result is `{ok:true, already_finished:false, state:"FINISHED", population_adopted:true, actors_active:true, combat_generation, committed_cleanup_receipt, cleanup:<actual receiver result>}`. These are intended runtime results, not effects observed during this work.
