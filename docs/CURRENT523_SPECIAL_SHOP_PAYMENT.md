# Existing specialized-supply shop payment bridge

Local follow-up, untested. No tests, compilation, game, rendering, CI, publication or merge.

Market/NPC payment reuses the existing `native_awakening_supply` owner rather than manufacturing generic receipts. Admission requires the existing owner's exact current-source record, the shop's whole original ItemClass row, the same source archive and an actually registered current typed DTO with its existing server/service/date/deletion holds intact. Only existing schema2 `source_awakening_supply` physical ownership is admitted here. The owner's supported-ID list is not a completed-content count; source wallets, absent registrations and unsupported source conditions remain under their existing owners.

`_special_payment_binding(original, amount)` selects actual unlocked, unequipped, non-selected-ammunition physical objects. Ascending physical ID is the explicit TWILIGHT custody policy. Each request separately retains physical_id, item_class_id, quantity, expected_quantity, expected_remaining and its immutable source_awakening_supply. Exact remaining quantities may span several source receipts; no receipt is combined or rewritten. Same-key mixed provenance and competing funded legacy keys still block payment. No alias, raw quest conversion, historical schema upgrade or regrant is performed.

`_prepare_native_payment` re-resolves the selection before calling `_prepare_special_payment`. The latter uses a temporary candidate-only NativeGrantView and sequentially calls the EXISTING `native_awakening_supply.prepare_debit(view, item_id, quantity, selected_physical_id)` and `matches_payload` for each selected object. Each result must consume only its selected source-owned object, contain no quest debit step, and leave the exact expected physical remainder and original receipt. The next selected debit starts from the previous result, so no whole-candidate merge overwrites an earlier debit. The view never saves, grants, installs or modifies the live world and is freed on either outcome.

The existing `_commit` freshly re-resolves and stages the same complete payment against live ownership, compares the prepared candidate, then writes inventory, physical quantities, all selected payment receipts, pending order and purchase counter in ONE save. Generic native payment additionally carries its existing consumption ledger. Failed staging abandons all candidate debits; save response errors retain the existing reload lock and do not authorize another purchase. Prices, source quantities, receipt schemas and old saves are unchanged. Claiming a paid order never charges payment again.

Still pending: mixed quest/legacy-origin choice and specialized output suppliers. The existing specialized owner supports broader origins for other callers; this shop bridge does not assume those are authorized shop payment semantics. No source reader, effect engine, item identity or gameplay formula is duplicated.
